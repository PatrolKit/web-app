## 4. Phases

### Phase 0 — Fix CDK conflicts with pre-existing resources

Two CDK stacks will conflict with resources that already exist in the account. Both must be
fixed before `cdk deploy` will succeed.

**Problem 1 — `PatrolKit-Shared` tries to create an SES email identity for `patrolkit.io`.**
This identity already exists and is fully verified with DKIM. CloudFormation will fail trying to
create a duplicate. Fix: remove the `ses.EmailIdentity` construct from `SharedStack`. Derive the
`sesIdentityArn` it exports directly from the known account/region:
```
arn:aws:ses:us-east-2:058264065670:identity/patrolkit.io
```

**Problem 2 — `PatrolKit-Network` must not create a new Route 53 hosted zone.**
(The original plan called for adding one.) A zone for `patrolkit.io` already exists
(`Z04621431O4OWAZ87K7NH`). Creating a second zone would produce a duplicate with no records and
break DNS. Any stack that needs the hosted zone ID references the hardcoded value directly.

**Acceptance criteria for Phase 0:**
- `pnpm infra:synth` completes with no errors
- The synthesized template contains no `AWS::SES::EmailIdentity` resource
- The synthesized template contains no `AWS::Route53::HostedZone` resource
- The SES send IAM policy in `PatrolKit-Api` still scopes to `patrolkit.io`

### Phase 3 — Populate JWT signing keys

The `patrolkit/jwt-keys` secret is created with placeholder values by CDK. Populate it with
a real Ed25519 key pair before the first container starts.

Use a temp file to keep values out of shell history:
```bash
node scripts/gen-keys.mjs
# Copy JWT_PRIVATE_KEY and JWT_PUBLIC_KEY values into /tmp/jwt-payload.json:
# { "JWT_PRIVATE_KEY": "<PRIVATE>", "JWT_PUBLIC_KEY": "<PUBLIC>" }

JWT_SECRET_ARN=$(aws --no-cli-pager secretsmanager describe-secret \
  --secret-id patrolkit/jwt-keys \
  --query ARN --output text --region us-east-2)

aws --no-cli-pager secretsmanager put-secret-value \
  --secret-id "$JWT_SECRET_ARN" \
  --region us-east-2 \
  --secret-string file:///tmp/jwt-payload.json

rm /tmp/jwt-payload.json
```

**Acceptance criteria:**
- `aws secretsmanager get-secret-value --secret-id patrolkit/jwt-keys --region us-east-2`
  returns a JSON object where neither value is the placeholder string `REPLACE`

### Phase 6 — App Runner custom domain + DNS cutover

> CloudFormation does not support this resource. Managed via CLI only.

**Note:** `patrolkit.io` currently resolves to `3.139.205.254` (an unattached EIP from the old
server). The site is currently down. Cutting over DNS will bring it back live on App Runner.

```bash
# Associate apex domain
aws --no-cli-pager apprunner associate-custom-domain \
  --service-arn "$SERVICE_ARN" \
  --domain-name patrolkit.io \
  --region us-east-2

# Associate www subdomain
aws --no-cli-pager apprunner associate-custom-domain \
  --service-arn "$SERVICE_ARN" \
  --domain-name www.patrolkit.io \
  --region us-east-2
```

Each response includes:
- `CertificateValidationRecords` — CNAME records for ACM certificate validation
- `DNSTarget` — the App Runner hostname to ALIAS

**In Route 53 (hosted zone `Z04621431O4OWAZ87K7NH`):**

1. Add the `CertificateValidationRecords` CNAMEs from both domain associations.
2. Replace the existing `patrolkit.io` A record (currently `3.139.205.254`) with an ALIAS A
   record pointing to the App Runner `DNSTarget`.
3. Replace the existing `www.patrolkit.io` A record (currently `3.139.205.254`) with an ALIAS A
   record pointing to the App Runner `DNSTarget`.

Check validation:
```bash
aws --no-cli-pager apprunner describe-custom-domains \
  --service-arn "$SERVICE_ARN" \
  --region us-east-2 \
  --query 'CustomDomains[*].{Domain:DomainName,Status:Status}'
```

Wait for both domains to show `Status: ACTIVE` (5–15 minutes after DNS propagates).

**Acceptance criteria:**
- Both custom domains show `ACTIVE` in App Runner
- `curl https://patrolkit.io/healthz` returns `{"status":"ok"}`
- Browser confirms TLS certificate valid for `patrolkit.io`

## 5. Post-deploy runbook

### Routine deployment

```bash
pnpm image:build
pnpm image:push
pnpm release
```

### Database access (for debugging)

RDS is in private subnets with no public access. Use AWS Systems Manager Session Manager
or a temporary EC2 bastion in the same VPC. Never open port 3306 to the internet.

### Rotating JWT keys

1. `node scripts/gen-keys.mjs` → store new values in `patrolkit/jwt-keys`
2. `pnpm release` — new container picks up the new secret
3. Existing access tokens signed with the old key expire within 15 minutes

### Scaling

Update `autoScalingConfiguration` in `infra/lib/api-stack.ts` and run `pnpm infra:deploy`.
